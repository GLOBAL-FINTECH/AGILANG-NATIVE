# Native AGILANG Blockchain Release Gates

This document prevents architectural scaffolding from being mistaken for a production-complete public blockchain.

## Implemented foundation

- canonical chain configuration and core transaction/block types
- SQLite block, transaction, state and metadata persistence
- deterministic account balances, nonces and state roots
- bounded mempool and replacement policy
- fee-aware block execution and rollback
- legacy and EIP-1559 fee settlement
- locally produced and imported block re-execution
- stake-weighted proposer selection
- attestations, justification, finalization and equivocation detection
- strict legacy/EIP-1559 raw transaction decoding and sender recovery
- HTTP JSON-RPC admission including `eth_sendRawTransaction`
- P2P handshake, sync planning, framing and snapshot protocol types
- finalized-ancestry protection in the production runtime

## Release-blocking gates

### GATE-01: Build and test proof

All blockchain crates must pass formatting, compilation, Clippy and tests on Windows and Linux. A release must contain the CI run URL and commit SHA.

### GATE-02: Canonical Genesis hash parity

`stable_json` must recursively sort every JSON object key before serialization. Transaction, Merkle, genesis and block vectors generated by the pinned Genesis commit must match byte-for-byte.

### GATE-03: Atomic database commit

The storage crate must expose one SQL transaction that commits:

- block and transactions
- resulting chain state
- execution receipts
- base-fee metadata
- Ethereum/Native hash aliases
- canonical-head update
- finality metadata

A process crash may not leave any subset visible.

### GATE-04: Embedded EVM

A production chain requires deterministic contract creation and calls, including stack, memory, storage, gas, logs, reverts, precompiles, fork rules, receipts and state commitments. The existing outbound EVM RPC client is not an execution engine.

### GATE-05: Imported block consensus verification

Imported blocks must verify validator signatures, slot eligibility, timestamp drift, execution result, state root, transaction root, receipt root, gas accounting, base fee and finalized ancestry before persistence.

### GATE-06: Real peer transport

The P2P protocol types must be connected to authenticated TCP/QUIC transport, bounded queues, peer scoring, duplicate suppression, block/transaction gossip, header sync, snapshot application and historical backfill.

### GATE-07: Validator key security

Compatibility HMAC keys must be replaced or explicitly restricted to private networks. Public networks require audited asymmetric validator keys, secure key storage, zeroization, signing domains and slashing evidence.

### GATE-08: RPC completeness

Required methods include raw submission, calls, estimation, code/storage queries, logs, fee history, filters and WebSocket subscriptions. Request authentication and administrative-method isolation are mandatory.

### GATE-09: AGILANG source and CLI exposure

Blockchain types and operations must be reachable from `.agi` source through semantic types, runtime ABI handles, code generation, standard-library modules, LSP support and documented CLI commands.

### GATE-10: Recovery and snapshots

The node must restore state, aliases, base fees, finality and mempool policy after restart. Finalized snapshots must include checksums and be verified before application.

## Completion definition

The blockchain is complete only when all ten gates pass against one pinned Native commit and one pinned Genesis reference commit. Until then the correct status is **Native blockchain implementation preview**.
